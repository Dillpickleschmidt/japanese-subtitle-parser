## Implementation Strategy

### Test-First Approach
For each pattern:
1. Review grammar_points_data.json for structure variants
2. Write tests in grammar-lib/src/tests/nX_patterns.rs with print_debug
3. Examine tokenization output
4. Implement matcher in grammar-lib/src/matchers/nX.rs
5. Run tests until passing
6. Remove print_debug calls
7. Verify with assert_pattern_range

### Kagome Tokenization Quirks
- Te-form can appear as both "て" and "で" (voicing)
- Verb conjugations: Check features[5] for conjugation form
- らしい as 助動詞 can mean "seems like" OR "typical of" (context-dependent)
- Compound words may tokenize as single token or separate tokens

### Patterns That May Be Tricky
- Particles with multiple meanings (の, で, に, etc.)
- Patterns requiring semantic disambiguation (らしい①/②)
- Wildcard patterns with variable intervening tokens
- Patterns with optional components

### Code Quality Standards
- Always use assert_pattern_range (not just assert_has_pattern)
- Test ALL structure variants from grammar_points_data.json
- Use realistic subtitle-quality sentences
- Include negative tests for similar-looking patterns
- Remove print_debug before committing
- Document undetectable variants with TODO comments
